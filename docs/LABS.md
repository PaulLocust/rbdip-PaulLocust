# Выполненные лабораторные

Каждая ветка продолжает предыдущую: `feat/lab1` → `feat/lab2` → `feat/lab3`
→ `feat/lab4` → `feat/lab5`. После финальной проверки результат объединяется с `main`.

## ЛР1 — разделение обязанностей

Исходный `OrderService` одновременно проверял входные данные, загружал товары,
рассчитывал сумму, сохранял заказ и имитировал отправку письма. Теперь он
координирует `OrderValidator`, `PricingCalculator`, `OrderWriter`, `OrderNotifier`.
Параллельные списки товаров и цен заменены одной записью `ValidatedItem`.
Коэффициенты скидок и пороги именованы, расчёт разбит на небольшие методы.
Транспорт email по-прежнему не настроен: уведомление записывается в журнал.

## ЛР2 — тесты и нормализация

`PricingCalculatorTest` фиксирует границы количества 10/11, суммы 1000,
скидки клиентов, купоны, порядок их применения, отрицательные значения,
пустой заказ, неизвестные коды и округление. Некорректные количества
отсекаются на уровне API; калькулятор сохраняет исходное поведение.

V2 выносит контакты в `customers`, связывает заказы и товары внешними ключами.
Одинаковые старые контактные записи объединяются. Если старой позиции нет
в каталоге с тем же названием и ценой, миграция сохраняет её отдельным товаром.
Это проверяется на заполненной БД в `NormalizationMigrationTest`.
В исходной схеме нет идентификатора клиента и связи позиции с товаром, поэтому
восстановить личность клиента или исходный товар точнее этих данных невозможно.

## ЛР3 — expand-contract

V3 добавляет и заполняет новые поля имени. Триггер поддерживает совместимость
старых и новых писателей. Новая версия приложения использует новые поля.
V4 удаляет старое поле и триггер после обновления всех экземпляров.
Порядок развёртывания и ограничения описаны в [MIGRATION_ROLLOUT.md](MIGRATION_ROLLOUT.md).
Собственный HTTP-тест создаёт и читает заказы четырьмя потоками во время contract.

## ЛР4 — запросы и границы модулей

`OrderQueryService` получает заказы, клиентов, позиции и товары через один
`JOIN FETCH`. Собственный тест проверяет ровно один запрос для 1 и 20 заказов
с несколькими позициями. Эталонный тест допускает максимум три запроса.

`review` использует публичный `PurchaseHistory` из отдельного пакета `purchase`.
Адаптер `OrderPurchaseHistory` скрывает репозитории заказов. Проверка покупки
теперь сопоставляет конкретный товар и имя, но, как и раньше, не запрещает
отзывы посетителям. Проверки модуля используют подмену интерфейса.

## ЛР5 — итоговая проверка

Добавлены проверки ошибок API и отсутствия частичных записей при отказе,
значения количества по умолчанию, ответов каталога и отзывов, а также
дополнительные сочетания скидок вокруг порога большой суммы.

Воспроизведение полного прогона при запущенном Docker:

```sh
mvn clean verify -Dmaven.test.failure.ignore=false
mvn org.pitest:pitest-maven:mutationCoverage
python scripts/write_score.py
```

Исходная конфигурация Surefire допускает продолжение сборки при падении теста,
поэтому для локальной проверки указан строгий режим. Конфигурация CI не менялась.
Эталонные тесты, V1 и критерии начисления баллов сохранены без изменений.

Отчёты: `target/surefire-reports`, `target/site/jacoco/index.html`,
`target/checkstyle-result.xml`, `target/pmd.xml`, `target/pit-reports/index.html`.

Результат локального прогона 2 ноября 2026 года: 54 теста без ошибок и пропусков,
покрытие строк 198/209 (94,74%), PIT — 16/16 обнаруженных мутаций (100%).
Все восемь гейтов `write_score.py` пройдены: 100/100.
Checkstyle — 0 замечаний, PMD — 10, суммарно ниже лимита 15.
Исходный скрипт не распознаёт пространство имён XML текущего PMD и выводит 0;
фактическое число проверено непосредственно по `target/pmd.xml`.
Это локальные результаты; GitHub Actions запускается после отправки коммитов.
